## Integer policy / exact configurable defaults

`FeedRankingPolicy` via `wedo.community.ranking.*`:

- freshness-weight600; social-weight150; engagement-weight150; recruitment-weight100. Nonnegative weights must sum1000. Interest weight0 because no valid viewer-interest source.
- half-life-seconds86400; actor-cap20.
- age=max(0, reference−created in seconds); freshness=floor(1000×86400/(86400+age)). Monotonic hyperbolic decay, half at24h, not a fixed cutoff.
- social=1000 only for an actual ACTIVE direct friend; otherwise0. FOF audience authorization remains a separate rule, not a global friend requirement.
- engagement=floor(1000×min(distinct eligible non-author actors,20)/20). An actor counts once across reactions and active comments combined; author self-engagement excluded. Active users only; blocked actors do not contribute to this viewer. Repeated comments/reactions cannot farm score. Contribution≤150,000.
- recruitment=1000 only for current eligible OPEN recruitment with future expiry, no past planned date, active authorized recruiter/group/policy, nonclosed/noncompleted linked Activity, available lifetime target/group capacity; else0. Contribution≤100,000. CLOSED/FILLED/EXPIRED/past plans may remain readable normal historical feed posts, receive no OPEN boost; existing separate OPEN discovery filtering unchanged.
- score=600×freshness+150×social+150×engagement+100×recruitment, integer0..1,000,000. Equal scores: created_at DESC, UUID canonical unsigned/string order DESC. No floats, score or internal features in client DTO/cursor.

## Stable bounded pagination

`CommunityFeedRanking`: PostgreSQL selects at most201 chronological eligible candidates using existing feed index, scores at most200, then freezes their order. Only IDs/timestamps/integer order are held in backend memory, no DTO or media bytes. Page20; before fetching older windows, chronological keyset boundary includes timestamp+UUID. Every later window retains original reference time/created-at ceiling. New posts after the reference wait for explicit refresh. Engagement/social changes cannot reshuffle an already-created window. Older windows are ranked when reached, so older posts remain traversable rather than permanently excluded by a top200 cutoff. Ranking is **within chronological windows**, not a global all-history sort.

Opaque UUID `nextBefore` maps to immutable version1 viewer-bound state, original expiry/reference, window and offset. Replay returns the same ordering subject to current eligibility. UUID guessing/cross-viewer/malformed/expired/evicted cursor yields400 `COMMUNITY_FEED_CURSOR_INVALID`, no partial data or silent rerank. Old pre-R8 For You post-ID cursors require fresh first-page load; field/type remains compatible. Friends/Profile/comment cursors stay chronological UUIDs.

Defaults `window-size=200` (20..500), `max-cursors=2048` (1..10000), `cursor-ttl-seconds=900` (1..3600). Cache is bounded, opportunistically expires and FIFO-evicts entries; windows are immutable/shared across page tokens. No background job, ranking DB, new schema or Redis behavior. **Single-instance V1 limitation:** restart, eviction or routing a cursor to a different instance requires explicit refresh. Multi-instance deployment needs sticky routing or a separately reviewed shared snapshot store, not a fabricated distributed guarantee. TTL never extends while paginating. Very old long sessions may need refresh.
